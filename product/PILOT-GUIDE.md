# superhuman-life-os pilot guide

This is actionable guidance for product maintainers. No users have been recruited, invitations sent, feedback collected, or platform runtime tests completed by this document.

## A suggested first round

Begin with a small group whose circumstances and intended uses differ clearly and who voluntarily agree to provide feedback. Starting with 3–5 people is reasonable. Fix recurring problems before expanding. You do not need sensitive identity data, income, or full personal histories to understand differences in use.

Share only the clean product package or combined file. Let each tester choose a platform and send the startup prompt themselves. Each person creates an independent instance, not a shared knowledge base.

Suggested feedback points are after the first build attempt, after the first real decision or practice cycle, and after the first Weekly Review. These are research suggestions; the package has not scheduled follow-ups or contacted anyone automatically.

## Collect useful, voluntary feedback

Testers may choose what to share. Raw journals are not a prerequisite:

| Observation | Suggested record |
|---|---|
| Getting started | Platform and describable configuration, whether files were read completely, and where setup stalled |
| Build state | Complete, incomplete, or awaiting verification, with actual evidence or gaps |
| Personal fit | Whether modules made sense and which misunderstandings needed correction; redacted examples are enough |
| First value | The specific prompt or result that helped, and what did not; completely unhelpful is a valid answer |
| Judgment or action | Changed decision, stronger grounds for keeping it, feasible next step, or no effect |
| Burden | Irrelevant questions, repeated confirmation, record maintenance, or notification costs |
| Reasons for stopping | Voluntary explanation; silence is not satisfaction or success |

Distinguish unsupported platform capability, failed setup, and lack of value after working setup. They require different improvements and should not all be blamed on user error.

## Compatibility record template

`Test date | Platform and actual environment | Tools/permissions | Storage | Later retrieval | Original records | Maintenance/inspection | State-aware invitations | Gaps | Evidence | Applicability limits`

Start with an empty record. Tool lists and official descriptions provide leads; a pass must come from acceptance in the actual configuration. One account passing does not establish support for every account, region, device, or version. External claims must state the environment and date.

## Before distribution

- No personal operating records, account details, local machine paths, or private life events are in the package.
- README, startup instructions, core rules, combined file, and version agree, with working references.
- The module registry starts empty and does not inherit the creator's life configuration.
- Known limitations, unfinished acceptance, and unverified outcomes are stated plainly.
- Delivery deduplication, instance isolation, exit, and update protection have concrete acceptance procedures.
- Feedback is voluntary, without default data uploads or unauthorized recipients.

Passing document checks makes the beta material ready to share; it does not replace runtime acceptance on the receiving platform. Product effectiveness, pricing, and general release remain separate decisions.

## Improvement order

Address trust failures first: incorrect records, mixing users' data, exceeded permissions, and repeated nudges. Then fix core build or retrieval blockers. Next reduce unnecessary onboarding and improve module proposals and first useful help. Add more features only with evidence from use.
